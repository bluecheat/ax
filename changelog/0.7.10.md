# 0.7.10 — 다음 task 가 의존을 봐요 · 완료 전에 룰을 대조해요 · 끝난 spec 에 후속을 이어 열어요 · 합의 리뷰 상한에서 사용자 승인

## 무엇이 좋아졌나 — 누구에게 체감되나

> spec 을 tasks 로 나눠 구현하는 사람에게 체감돼요. 다섯 가지 모두 실사용 프로젝트에서 실제로 겪은 마찰이에요.

- **다음 task 가 의존을 지켜요.** `mark-task.sh --next` 가 `의존:` 을 무시하고 펜스 밖 첫 미완료 task 를 골라,
  아직 안 끝난 task 에 기대는 일을 먼저 시작했어요. 이제 의존이 전부 `[x]`·`[~]` 인 첫 task 를 골라요
  (`tasks-plan.sh` 와 같은 파서). 미완료가 전부 막혀 있으면 "끝났다" 가 아니라 `warning` 과 막힌 task ·
  풀리지 않은 의존(없는 ID 는 따로)을 돌려줘요 — 완료 게이트로 잘못 넘어가지 않아요.
- **새 파일이 관례 위치로 가요.** `files:` 목록이 관례 위치(같은 레이어의 별도 하위 디렉토리)를 빠뜨리면,
  구현자가 목록을 지키려고 새 타입을 목록 안 파일에 끼워 넣었어요. spec-tasks 는 새 파일 경로를 적기 전에 이웃을
  grep 하고, 레인·위임 브리프는 "목록과 관례가 충돌하면 멈추고 보고" 를 실어요.
- **완료 전에 룰을 대조해요 (G7).** 위반된 룰(이름 룰, 레이어 룰)은 편집 때 훅이 실제로
  매칭해서 안내했어요. 그런데 안내 훅은 룰 **경로**만 주고, `rule-read-gate.sh` 는 그 파일을 **읽었는지**만 봐요 —
  읽은 룰을 지켰는지, 새 파일이 이웃 관례를 따랐는지는 아무도 대조하지 않았어요. 이제 새 컨텍스트의
  `rules-auditor` 가 변경 파일마다 걸린 룰과 새 심볼의 이웃 관례를 대조해 `review-rules.md` 첫 줄에 verdict 를 쓰고,
  완료 게이트가 G6 과 같은 필수 여부(size L 이상 · M×L3)로 읽어요.
  - 편집 훅도 조금 더 줘요 — 세션에서 처음 매칭될 때 룰 파일 경로와 함께 룰 제목(`SP-…: …`)을 붙여요.
- **끝난 spec 에 후속 작업을 이어 열어요.** `reset-task.sh` 로 닫은 작업은 `--activate` 가 "작업이 없어요" 로 실패해
  새로 열면 spec 연결이 끊겼어요. `update-task.sh --start --follow-up <spec>` 가 spec_id · spec_dir · spec_tier 를
  이어받고 `follow_up_of` 를 남겨요.
- **합의 리뷰 상한에서 사용자가 승인할 수 있어요.** 상한에 닿은 뒤 남은 차단이 기계적 수정뿐이어도 진행하려면
  intent_notes 에 손으로 적어야 했고, `--status` 는 그걸 몰라 pass 가 안 됐어요. `spec-review.sh --override --reason`
  이 지금 sha 에 누가 · 언제 · 왜 를 `review-override.md` 로 남기고 `--status` 가 그걸 인정해요. 본문을 또 고치면 풀려요.

## 바뀐 것

- `common.sh` `goax_tasks_parse` — tasks.md 실행 그래프 파서 하나 (`tasks-plan.sh` · `mark-task.sh --next` 공용).
  `의존:` 줄은 T-ID 만 읽고, T-ID 가 없는 다른 표기는 풀리지 않는 의존으로 남겨요 (오타가 "의존 없음" 으로 통과하지 않게). `없음 (첫 task)` 처럼 없음·none·- 뒤에 설명을 붙인 건 의존 없음이에요

- `rules-audit-scope.sh` (신규) — 변경 파일마다 걸린 spirit·모듈 룰(편집 훅과 같은 매칭 함수) · 상시 룰 · 새 파일
