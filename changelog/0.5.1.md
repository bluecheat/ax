# 0.5.1 — 문서가 앞서 있던 엣지 셋을 코드로

> 0.5.0 을 오케스트레이션 스택 여섯 층(격리 · 분해 · 실행 그래프 · 컨텍스트 경계 · 검증 · 통합)에
> 맞대어 봤더니, **분해와 결정적 검증은 강한데 실행 그래프로 이어지는 엣지가 없었어요.**
> `parallel`(지금의 `lane`) 은 레인을 그리고 "실행은 spec-implement" 라고 넘기는데 받는 쪽은 첫 빈 체크박스를
> 순차로 집는 코드 그대로였고, triage 매트릭스는 "spec-validate + evaluator" 를 배정하는데
> evaluator 를 부르는 skill 이 없었어요. 오늘 잡은 "CLAUDE.md 가 up 보다 앞서 있다" 와
> 같은 종류의 결함이 두 군데 더 있던 거예요. 이 판은 그 셋을 잇는 판이에요.

## 레인 원장 — `lanes-dispatch.sh`

코디네이터의 기억은 컨텍스트 창 안에만 있어요. 어떤 task 를 어느 레인에 넘겼고 무엇이
돌아왔는지가 전부 창 안에 있는데, 그 창은 압축되고 세션이 죽으면 사라져요. 레인 8개가
전부 idle 이 됐을 때 체크박스는 24/36 이었던 사고(idle ≠ 완료)와, 세 에이전트가 산출물을
완성해 놓고 전송하지 않아 아무것도 도착하지 않은 사고 둘 다 "누구에게 뭘 보냈고 뭘 받았는가"
가 파일에 없어서 생겼어요.

그래서 원장을 **tasks.md 안에** 둬요 — 기계가 읽는 유일한 진행 문서니까요. task 줄 아래
continuation 세 줄이에요 (`의존:` 과 같은 자리):

```
      레인: A                       ← --assign  (lane 이 배정을 정한 뒤)
      디스패치: 2026-09-06T03:12Z   ← --dispatch (레인을 띄우기 직전)
      보고: 2026-09-06T04:02Z       ← --report  (산출물을 **받은** 시점)
```

손으로 안 적어요. `--status` 가 네 가지를 판정해요 — 보고 안 받은 디스패치 · 보고 없이
켜진 체크박스 · 같은 파일을 두 레인이 소유 · 레인 없는 미완료. 그리고 **`--dispatch` 는
파일 소유 충돌이 있으면 거부해요.** 계획서가 권고하던 것을 스크립트가 막는 자리가 하나 생겼어요.

소유자는 여전히 정하지 않아요. 배정은 판단이라 `lane` 이 사람과 하고, 여기선 기록과
검사만 해요. `tasks-plan.sh` 헤더가 긋는 선("자동 실행하지 않아요") 과 같은 선이에요.

## `spec-implement` — 받는 쪽을 만들었어요

**진입 게이트 (§1.5).** `tasks-plan.sh` 의 violations 가 있으면 진행하지 않아요. `lane` 을
건너뛴 경우를 위해 있어요 — 계획을 안 거치면 방어가 0 이던 것을 실행자가 한 번 더 검사해요.
그다음 원장을 읽어 `레인:` 이 하나라도 있으면 **레인 모드**, 없으면 지금까지의 순차예요.

**레인 모드 (§3.5).** 이 세션은 코디네이터예요. ready 를 레인별로 묶고 → `--dispatch` 로 원장에
먼저 적고 → `goax:lane-worker` 를 한 메시지에 같이 띄우고 → 보고가 오면 `--report` 로 적고 →
**보고에 인용된 검증 명령을 코디네이터가 직접 다시 돌린 뒤에만** 체크박스를 켜요. 레인 A 가
끝나 의존이 풀리면 B 를 기다리지 않고 바로 다음을 띄워요 — `tasks-plan.sh` 가 일부러 배리어를
안 만든 이유가 여기서 실현돼요. `phase_gate` 의 사람 확인은 Phase 경계가 아니라 **레인 보고를
받은 시점**이에요. Phase 와 레인은 1:1 이 아니라서요. 종료는 ready·blocked 가 비고 원장의
보고 대기가 0 일 때이고, 그 뒤 통합 검증(`zero-verify.sh`) + 이름 대조를 한 번 더 해요.

`lane-worker` 는 이제 체크박스를 켜지 않아요. tasks.md 는 레인의 소유 파일이 아니에요.
보고는 task ID 단위로 완료/미완료를 적어요 — 코디네이터가 그 ID 로 원장에 찍으니까요.

**완료 게이트 (§8).** 게이트가 `complete` 라고 해도 evaluator 가 남았을 수 있어요. 아래 §evaluator.

## `tasks-gate.sh` — G5 · G6

- **G5 원장**: `dispatched_unreported`(디스패치됐는데 보고 없음) · `done_without_report`(디스패치된
  task 가 보고 없이 `[x]`) 가 비어야 완료예요. 레인이 자기 체크박스를 켜면 여기서 잡혀요.
  원장 필드가 없는 spec 은 영향이 없어요.
- **G6 검증자**: `<spec>/review.md` 첫 줄 `verdict: 진행 | 보강 필요 | 재논의 필요` 를 읽어요.
  활성 spec 의 size×risk 가 **L 이상 · M×L3** 이면 필수 — review.md 가 없으면 미완료. 필수가
  아니어도 verdict 가 `진행` 이 아니면 막아요. 받은 리뷰를 무시하고 완료할 수는 없어요.
  필수 매트릭스의 SSOT 는 `tier-from-state.sh` 의 새 `evaluator` 필드예요.

pre-commit 훅(`spec-completion-gate.sh`)도 같은 항목을 보여줘요.

## evaluator — 엣지와 산출물

`spec-implement` §8 이 task 0건 남은 시점에 `goax:evaluator` 를 **새 컨텍스트로** 띄워요.
브리프에는 spec · ADR · diff 범위 · 산출물 경로 넷만 들어가요. 이 대화를 넘기지 않아요.

evaluator 는 결과를 대화로만 돌려주지 않고 **`review.md` 를 직접 써요.** 코디네이터가 받아
적으면 검사받는 쪽이 검사 기록을 쓰는 게 되니까요. 첫 줄이 verdict 이고, G6 이 그 줄을 읽어요.
`보강 필요` 면 지적을 task 로 옮기고 §3 으로 돌아가고, 끝나면 evaluator 를 다시 띄워요.
`재논의 필요` 면 halt 예요 — spec 자체를 다시 봐야 한다는 뜻이라서요.

CONCEPTS §5.3 이 말하던 Generator/Evaluator 분리의 실체가 이거예요 — **평가 기록을 구현 세션이
쓰지 않는 것.**

## `parallel` → `lane` — 이름을 장치에 맞췄어요

0.5.0 이 `parallel` 로 출고한 skill 을 `lane` 으로 바꿨어요. "병렬" 은 목표고 "레인" 이 장치예요 —
이 skill 이 정하는 건 병렬 여부가 아니라 **레인을 어떻게 가르고 누가 어떤 파일을 갖는가**이고,
에이전트(`lane-scout`·`lane-worker`)와 스크립트(`lanes-hotfiles.sh`·`lanes-dispatch.sh`)는
이미 그 이름이었어요. 세 이름이 한 어휘를 가리켜야 문서와 코드가 서로를 찾아요.
"병렬로 돌리자"·"parallel" 은 트리거 단어로 그대로 남아요. 슬래시는 `/lane` 이에요.
