# UX 라이팅 — 느낌이 아니라 논리로

예시는 한국어지만 절차(정보 → 상황·동기·기대 결과 → 핵심 하나 → 보이스)는 언어와 상관없어요. 한국어 화면의 문체·줄바꿈·표기 관례는 `locale-ko.md`.

## 1. UX 라이팅이 무엇이고 무엇이 아닌가

- **정의**: 인터페이스 안에서 사용자와 대화하는 문장. 사용자가 막힌 지점에서 **다음 행동**을 할 수 있게 도와요. 이탈을 막고 전환을 올리는 문제 해결 도구예요.
- **카피라이팅과 달라요**: 카피는 브랜드 감정으로 끌어오는 글("당신의 입장을 가볍게"). UX 라이팅은 과업 순간에 필요한 정보를 주는 글("사이즈 선택을 도와드릴까요? 평소 사용하시는 사이즈를 입력해 주세요").
- **아닌 것**: 자극적·트렌디한 마케팅 문구, 맥락 고민 없이 단어만 예쁘게 바꾸는 작업.
- 기능을 구현하고 완성하는 것은 일의 절반이고, 나머지 절반은 그 기능이 사람에게 어떻게 말하는지에 달려 있어요.

## 2. 판단 절차 — 이 순서로

| 단계 | 질문 | 왜 |
|---|---|---|
| 1 관점 전환 | "어떻게 말할까(말투)가 아니라 **무엇을** 말할까(정보)?" | 종결어미·말투는 주관적이라 합의가 안 됨. 정보 축은 합의됨 |
| 2 상황·동기·기대 결과 | "지금 사용자의 상황은? 동기는? 이 화면의 기대 결과는?" | 이게 있어야 행동 유도 논리가 선다 |
| 3 핵심 정보(primary content) | "이 화면에서 제일 중요한 정보 **딱 하나**는?" | 공간과 인지 용량이 한정. 다 넣으면 다 묻힘 |
| 4 First Survive, Then Thrive | 정보 구조·위계로 먼저 살아남고, 그다음 브랜드 보이스·말투 | 정보가 서지 않은 문장은 말투를 다듬어도 읽히지 않음 |
| 5 문제 해결 프레임 | "이 문구가 어떤 문제를 풀고 이탈을 얼마나 줄이나?" | "내 문장이 더 좋다"는 설득이 안 됨 |

## 3. 좋은 문구의 기준

- **소리 내어 읽기** — 눈으로 괜찮아 보여도 입으로 읽어 어색하면 고쳐요. "입력값이 유효하지 않습니다"가 대표 탈락.
- **한 화면 하나의 목적** — 화면이 사용자에게 기대하는 역할은 하나. 문장 하나엔 메시지 하나.
- **익숙한 단어를 의심** — 확인·완료·실패·취소를 관성으로 쓰지 않아요. '완료'만 있으면 뭘 완료했는지 모름 → "주문이 완료됐어요". '실패'를 반복 경험시키면 이탈.
- **중복 워딩 제거** — 한 화면에 같은 명사가 여러 번이면 무엇을 가리키는지 헷갈림. 수량·정보만 남겨요.
- **다음 행동 안내** — 상태만 알리지 말고, 유의할 점이나 취할 행동을 구체적으로.
- **첫 방문자 시각** — 처음 쓰는 사람의 눈으로 "여기서 뭘 해야 하지?"가 바로 보이나.

## 4. 전·후 예시

| 화면 | Before | After | 이유 |
|---|---|---|---|
| 배달 앱 배달 지연 알림 | "속상하셨죠?" (말투 접근) | 정보 축 셋: ① 죄송한 마음 ② 쿠폰 제공 ③ 재발 방지 약속 | 말투는 진정성 평가가 갈림. 정보 축은 합의됨 |
| 배달 앱 장바구니 쿠폰 업셀 | "3,000원 더 담으면 5,000원 할인 가능" | '가능/받을 수 있어요' 말투 고민을 멈추고 빠진 핵심어 **'쿠폰'**을 넣음 | 목적이 쿠폰인데 쿠폰이 없었다 |
| 사장님용 앱 영업 임시 중지 | "사장님 혹시 바쁘세요? 영업 임시 중지 기능을 사용하고 주문 처리에 집중해 보세요" | "영업 임시 중지를 자동 설정해 보세요 (주문 처리가 어려운 상황에 쓰세요)" | 후킹 질문 대신 기대 결과를 맨 위에, 동기를 구체적으로 |
| 응모 서비스 응모 상세 | "응모권", "사용한 응모권", "보유 응모권" 중복 | "사용 수량", "보유 N장", "사용 N장" | 지금 쓸 수량인지 이전 내역인지 헷갈림 |
| 시스템 메시지 | "완료", "실패", "입력값이 유효하지 않습니다" | "주문 완료", "주문이 완료됐어요", 쉬운 대화체 안내 | 맥락 없음·부정어·읽으면 어색 |

## 5. 상황별 규칙

| 자리 | 원칙 | 피할 것 |
|---|---|---|
| 버튼·CTA | 눌렀을 때 얻는 **기대 결과**를 문장으로. 맥락 담긴 유기적 문장 | 맥락 없는 "확인"·"완료", 수단이 빠진 "할인 가능" |
| 에러·예외 | 소리 내어 읽어 자연스러운 대화체. 상황 + 다음 행동. | "입력값이 유효하지 않습니다", 단정적 "실패" 반복 |
| 알림·푸시·메시지 | 말투보다 **필수 정보 축**을 먼저 세우고 구조화. 제목 = 무슨 일(명사 2~8자), 본문 = 그래서 이제 할 수 있는 것(20~35자). 로컬 예약이면 어느 시각·요일에도 참인 말만 (`locale-ko.md` §3) | "속상하셨죠?" 류 질문형 위로, 예약 시점에 참인지 모르는 상태 약속("7일째예요"·"배지를 받아요") |
| 제목·라벨 | 한 화면 하나의 목적, 중복 명사 제거 | 같은 단어 반복, 시선 끌기용 질문 |
| 한자어 | 가능·불가·유효를 의심. 맥락 따라: 환불처럼 예민하면 "환불이 불가해요"도 되지만 브레이크 타임엔 "잠깐 주문이 어려워요" | 딱딱한 시스템 한자어 |
| 숫자·수량 | 명사를 떼고 "보유 N장"처럼 숫자·단위 중심 | "보유 응모권 N개" 식 중복 |

표에 없는 자리(빈 상태·온보딩·권한 요청·확인 대화상자·폼 라벨·플레이스홀더)는 위 절차(§2)로 스스로 유도해요. 이 파일이 안 다룬다고 규칙이 없는 게 아니에요.

## 6. 톤앤보이스 정하기와 가이드 체화

- 말투부터 정하면 주관에 갇혀 합의가 안 돼요. **정보 위계 → 보이스** 순서.
- 처음부터 거대한 가이드북을 만들지 않아요. **가장 많이 쓰는 핵심 화면 10개**(확인 버튼·에러 메시지 등)부터 가볍게 정해요.
- 팀원이 가이드를 암기하게 하지 말고, 실제 Figma·프로젝트 케이스를 같이 고치며 **체화**시켜요.

## 7. 설득 구조 — 팀에 문구를 통과시키는 법

1. 바꾼 문장을 먼저 보여 주지 않아요. **의도·배경·맥락·근거**부터 설명해요.
2. 반대가 오면 성격을 갈라요: 방향이 다른가(논리 재정립) vs 더 나은 표현을 원하나(교체로 해결).
3. 의견이 갈리면 "가장 중요한 정보 딱 하나만 꼽는다면?"으로 되돌려요. 근거는 공간 제약과 인지 한계예요.
4. 문제 해결 프레임: "기존 문장은 다음 행동을 안내하지 못해 이탈이 난다. 이렇게 바꾸면 이탈을 줄인다." 비즈니스 임팩트(전환·매출)로 말해요.

## 8. 배포 전 체크리스트

- [ ] 정보 위계가 먼저 섰나 (First Survive) — 말투 고민은 그다음
- [ ] 이 화면의 핵심 정보와 기대 역할이 하나인가
- [ ] 사용자의 상황·동기와 기대 결과가 구체적 낱말로 있나
- [ ] 소리 내어 읽어 자연스러운가
- [ ] 확인·완료·실패·취소를 관성으로 쓰지 않았나, 맥락이 붙었나
- [ ] 한 화면에 같은 명사가 중복되지 않나
- [ ] 처음 온 사람의 눈으로 다음 행동이 보이나

## 9. LLM 으로 문구 쓸 때

- **쓰는 법 셋**: 초안 빠르게 뽑기 · 검토 도구("이 문장을 처음 본 사람이 이해할까?", "내 맥락이 담겼나?") · 역할별 에이전트(PM 관점·디자이너 관점)로 토론.
- **프롬프트엔 맥락**: "에러 메시지 써 줘"가 아니라 상황("결제에서 네트워크 오류가 났을 때") + 대상("처음 쓰는 사용자") + 보이스("친절하고 명확한 톤").
- **한계**: AI 는 맥락 없이도 그럴듯하게 써요. "왜 이 문장이 이 맥락에 필요한가"의 최종 판단은 사람.
- **사람이 반드시 검수하는 셋**: 이 화면에서 사용자의 감정 상태 · 다음 행동이 정확히 안내되나 · 브랜드 보이스와 맞나.

### 9-1. 제품 안에서 LLM 이 문구를 매일 만들 때 — 지시문의 예시가 곧 출력이다

지시문(프롬프트)으로 결과 문장을 생성하는 서비스에서 실측한 규칙이에요(135건 표본을 아홉 번 재측정).

- **예시 문장은 규칙보다 세게 작동해요.** 좋은 예로 넣은 문장이 통째로 옮겨져요("한 줄이면 충분해요" 86/135건). 어느 날에나 맞는 예일수록 더 많이 옮겨져요. 예는 그날에만 맞는 구체 장면(물건·사람·시간·장소)으로 써요.
- **나쁜 예로 인용한 문장도 옮겨져요.** "이렇게 쓰지 마"라며 문장을 적으면 그 문장이 출력돼요(43/135). 나쁜 예는 문장 대신 꼴("종류 이름을 주어로 세운 질문")로 설명해요. 조각 인용("사람들과는…")만으로도 되살아나요.
- **예시는 한도 안에 있어야 해요.** 예 질문이 27자인데 상한이 24자면, 옮겨 쓴 출력이 전부 길이로 버려지고 기본값으로 떨어져요. 예시를 넣으면 글자 수부터 세요.
- **하나를 막으면 옆 자리로 새요.** 요일로 여는 헤드라인을 막자 "오늘은 ~날이에요"로 옮겨 갔어요. 여는 말을 막지 말고 **첫 어절에 무엇이 와야 하는지**(할 일의 대상)를 적어요.
- **결은 한 줄이 아니라 여러 줄로.** 결이 다른 예 다섯 줄을 주면 한 문장으로 수렴하지 않아요.
- **느낌 말 끝을 이득으로 바꿔요.** "가벼워져요"·"풀려요"·"굴러가요"는 무엇이 좋아지는지가 빠진 말이에요. "시간이 남는다·답이 온다·약속이 잡힌다·돈이 덜 나간다"처럼 생기는 것을 낱말로 적게 해요(51% → 10%).
- **세어서 판단해요.** 요일 시작 비율·반복 구절 상위 10·서로 다른 헤드라인 비율처럼 셀 수 있는 지표를 개정 전후로 재요. 눈으로 몇 개 읽고 판단하면 수렴을 못 봐요.
- **폴백 경로를 의심해요.** 이상한 기본 문장이 반복되면 모델보다 "버려지면 무엇이 대신 서는가"(길이 초과·종류 불일치·데이터에 실린 기본값)를 먼저 확인해요. 원문 응답 로그가 증거예요.

## 10. 흔한 실수

- 정보(What) 전에 말투(How)부터 고민
- 공급자 관점으로 한 화면에 다 밀어 넣기
- 후킹 질문("바쁘세요?")에만 치중
- 트렌디·자극적 카피에 집착
- 관성 단어(확인·완료·실패·취소) 그대로
- 한 화면 안 같은 단어 남발
- 처음부터 완벽한 가이드북 욕심
- AI 에 맥락 판단·최종 검수까지 맡김
- 만든 사람 눈으로만 보기

## 11. 핵심 원칙

- 말투보다 정보에 초점을 맞춰요. 말투는 굉장히 주관적이라 합의가 안 돼요.
- First Survive, Then Thrive — 정보 위계가 먼저, 보이스는 그다음이에요.
- 가장 중요한 정보가 무엇인지부터 물어요.
- 하나의 문장에 하나의 메시지만 담기듯, 한 화면에는 전달하려는 목적이 하나여야 해요.
- 익숙한 문장을 의심해요. 사용자가 실패를 반복 경험하는 것도 이탈 요소예요.
- 문장보다 먼저 설득해야 하는 것은 어떤 의도와 맥락으로 작업했는지에 대한 설명이에요.
- 왜 이 문장이 이 맥락에서 필요한가에 대한 최종 판단은 결국 사람이 해요.

## 12. 금지어 전수 검색 — 한국어 목록과 다른 언어로 옮기는 법

규칙을 알아도 에러 토스트에 "결제에 실패했어요" 가 새어 나와요. 그래서 금지어는 **눈으로 훑지 않고 검색해서 건수를 적어요.** 0건이라야 게이트를 통과해요.

**한국어 목록 (기본)**

| 낱말 | 왜 | 바꾸는 방향 |
|---|---|---|
| `실패` | 사용자를 실패한 사람으로 만들고, 반복되면 이탈해요 | "결제가 진행되지 않았어요. 카드를 바꾸거나 잠시 후 다시 시도해 주세요" — 상황 + 행동 |
| `불가` | 시스템 한자어. 이유도 대안도 없어요 | "지금은 주문할 수 없어요. 오후 5시에 다시 열어요" |
| `유효하지` | 소리 내어 읽으면 탈락하는 대표 문장 | 무엇이 틀렸는지: "휴대폰 번호 11자리를 입력해 주세요" |
| 단독 `확인` | 무엇을 확인하는지 없음 | 버튼은 결과 동사("320,000원 결제하기"), 정보 알림만 "알겠어요" 류 |
| 단독 `완료` | 무엇이 끝났는지 없음 | "9월 21일 04:30 2명 예약됐어요" — 대상·수량·시각 중 둘 |
| `오류가 발생` | 원인도 행동도 없는 시스템 보고 | "연결이 끊겼어요. 연결되면 자동으로 다시 보낼게요" |

검색은 **(가) 문구가 모인 파일**(strings · copy · i18n)과 **(나) design-spec 표 4 의 "문장" 열**에서만 해요. design-spec 파일 전체를 grep 하면 표의 "유형" 열(`완료` · `오류`)과 규칙 설명 문장까지 걸려서 건수가 늘 0 이 아니에요. 화면 파일에 리터럴 문구가 흩어져 있으면 검색이 안 되니, 문구는 한 파일로 모아요.

```bash
# 경로는 프로젝트에 맞게 — 문구 파일이 여럿이면 공백으로 이어요 (비워 두면 fw 가 입력을 기다려요)
COPY="src/strings.ts"
SPEC="docs/design/design-spec.md"
# 금지어 — 단독 확인·완료는 앞뒤가 글자·숫자가 아닐 때만 ('확인' · >확인< · "결제 완료" 는 걸리고 "확인하기" · "확인할" 은 안 걸려요)
fw() { perl -Mutf8 -CSD -ne 'print "$ARGV:$.: $_" if /실패|불가|유효하지|오류가 발생|(?<![\p{L}\p{N}])(?:확인|완료)(?![\p{L}\p{N}])/; close ARGV if eof' "$@"; }
# 표 4 의 "문장" 열만 — 표 4 제목부터 다음 제목 전까지, 머리 두 줄(제목 행 · 구분선)을 빼고 다섯째 필드
spec_lines() { awk -F'|' '/^##+ *표 4/ {on=1; n=0; next} on && /^#/ {on=0} on && /^\|/ && ++n > 2 {print FILENAME ":" NR ":" $5}' "$SPEC"; }

fw $COPY                                   # (가) 문구 파일
spec_lines | fw                            # (나) 표 4 문장 열
{ fw $COPY; spec_lines | fw; } | wc -l     # 건수 — 표 4 아래와 게이트 표에 이 숫자를 적어요
```

grep 대신 perl 을 쓰는 건 한글 경계 때문이에요 — `grep` 의 `[가-힣]` 범위와 `[[:alnum:]]` 은 grep 구현 · 로케일마다 한글을 다르게 다뤄요. perl 의 `\p{L}` 은 어디서나 같아요. 스펙 템플릿 원본에 돌리면 0건이 나와야 해요.

**다른 언어로 옮기는 법** — 낱말을 번역하지 말고 **역할**을 옮겨요. 어느 언어든 같은 다섯 자리가 있어요.

| 역할 | 한국어 | 영어 예 | 왜 막나 |
|---|---|---|---|
| 사용자 탓으로 읽히는 실패어 | 실패 | failed, invalid, illegal | 사람을 실패자로 만들어요 |
| 이유 없는 금지어 | 불가 | not allowed, forbidden, cannot be processed | 대안이 없어요 |
| 시스템 보고어 | 오류가 발생 | an error occurred, something went wrong (단독), unknown error | 원인·행동이 없어요 |
| 맥락 없는 확인어 | 단독 확인 | OK (정보 알림 밖에서), Submit, Confirm (단독) | 결과를 말하지 않아요 |
| 맥락 없는 완료어 | 단독 완료 | Done, Success, Completed (단독) | 무엇이 끝났는지 없어요 |

프로젝트가 다른 언어면 이 표의 둘째 열을 그 언어 낱말로 채워 design-spec 표 4 아래에 적고, 그 목록으로 검색해요. 낱말이 정해지지 않은 언어라면 "결과 동사 없이 끝나는 버튼 라벨" · "원인과 행동이 없는 오류 문장" 두 꼴을 눈으로 전수 확인하고 리포트에 그렇게 적어요.

## 13. SKILL.md 의 문구 순서 10단계 상세

1. **말투가 아니라 정보** — "어떻게 말할까" 를 멈추고 "무엇을 말해야 하나" 의 정보 축부터. 말투는 주관이라 합의가 안 되고, 정보 축은 합의돼요.
2. **상황 · 동기 · 기대 결과** — 사용자가 지금 어떤 상황이고, 무엇을 원하고, 이 화면을 지나면 무엇을 얻는지 한 줄씩.
3. **핵심 정보 하나** — 한 화면 하나의 목적, 한 문장 하나의 메시지.
4. **정보 위계로 먼저 살아남고, 그다음 보이스** (First Survive, Then Thrive).
5. **소리 내어 읽기**.
6. **익숙한 단어 의심** — 버튼 라벨은 행동 동사형("수거 신청하기" · "3크레딧으로 열기"). "신청 완료" · "등록됨" 같은 **상태어를 버튼에 쓰지 않아요** — 누르기 전 버튼이 끝난 상태를 말하면 이미 됐다고 읽어요. 보조 버튼도 "취소" 대신 "다음에 할게요" 처럼 무엇을 하는지.
7. **단위를 먼저 확정** — 결제·수량 문구는 화면의 단위(원 · 크레딧 · 장 · 회)를 하나로 잡고 섞지 않아요. 크레딧으로 여는 앱에서 "N원 결제하기" 가 튀어나오면 단위가 안 잡힌 거예요.
8. **같은 화면에 같은 명사 반복 금지** — "응모권 · 사용한 응모권 · 보유 응모권" → "보유 3장 · 사용 1장".
9. **결론 줄 바로 아래에 겨루는 줄을 두지 않아요.** 헤드라인이 할 일이면 그 밑은 비우거나 같은 주제의 보조여야 해요. 이유 문장("~라서요")이나 다른 주제의 근거가 붙으면 두 줄이 결론을 다퉈요. 근거는 목록 끝의 닫는 줄이나 근거 행으로. 헤드라인은 요일 · "오늘은" 같은 여는 말이 아니라 **할 일의 대상**(답장 · 장바구니 · 점심 약속)으로 열어요.
10. **약속은 보여 주는 순간 참이어야 해요.** "배지를 받아요" · "7일째예요" 처럼 사용자 상태를 말하는 문구는 그 상태를 확인하고 보여 줄 때만. 미리 예약하는 알림, 캐시된 카드, 오프라인 화면은 어느 시각·상태에도 참인 말(질문형 · 기능 안내)로.

문구 지적은 리포트에 `[W 정보축]` · `[W 관성어]` · `[W 중복]` · `[W 낭독]` · `[W 단위]` · `[W 약속]` 처럼 W 를 붙여 시각 패턴(P)과 구분해요. 설득이 필요하면 "이 문장이 더 좋다" 가 아니라 **"기존 문장은 다음 행동을 안내하지 못해 이탈이 난다. 이렇게 바꾸면 줄어든다"** 로 말해요.
