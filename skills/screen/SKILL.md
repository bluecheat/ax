# screen — 화면 설계 · 리뷰 · 실측

한 줄 신조: **"흰 바탕 위에서 글자 크기와 여백만으로 위계를 세우고, 강조는 딱 하나에만 준다."**
꾸미지 않고 레이아웃 구조부터 세워요. 말이 아니라 숫자로 증명하고, 재기 전엔 보여 주지 않아요.

## 시작 전 필수

`.ax/spirit/values.md`, `tone.md` 따라요. 사용자에게 보이는 문구는 `~해요` 체, 표시 기호는
`.ax/docs/reference/symbols.md` 어휘만 써요.

## 0. 이 skill 의 범위 — 외부 의존 0

이 skill 은 **판단**(모드 · 보는 눈 · 고치는 순서 · 게이트 · 판정)을 맡고, **실행**(만들기 → 렌더링 →
재기 → 고치기 → 리포트)은 `screen-designer` 에이전트에게 **새 컨텍스트로** 넘겨요 (§10). 그리고 돌아온
리포트를 첫 줄의 verdict 로 판정해요 (§11). 만든 쪽이 자기 결과를 평가하면 같은 맹점으로 통과시켜요.

**이 skill 은 외부 도구 없이 끝까지 돌아요.** 보는 눈 · 실무 수치 · 부품 16종 · 화면 18종 · 문구 절차 ·
디자인 시스템이 없을 때 쓰는 기본 토큰 세트가 전부 이 skill 의 `references/` 안에 있어요. Figma ·
디자인 시스템 MCP · 화면 레퍼런스 MCP(Mobbin 류) · 브라우저 자동화 · 시뮬레이터 · 이미지 라이브러리는
**있으면 빨라지는 가속기**예요. 무엇이 있는지는 기억으로 가정하지 않고 `design-caps.sh` 로 찾아요.
없으면 `references/capabilities.md` 의 대체 수단으로 진행하고, 렌더링·측정을 못 했으면 리포트에
**"실측 아님"** 이라고 적어요. **스크린샷 경로와 px 숫자 없이 "측정했다" · "확인했다" 고 쓰지 않아요.**

프로젝트에 디자인 시스템 · 토큰 · 가이드가 있으면 **수치는 그쪽이 이겨요.** 이 skill 의 진짜 값은
보는 눈과 고치는 순서예요. 충돌하면 프로젝트 규칙을 따르고, 그 규칙이 이 화면에서 왜 문제를 못
잡는지만 지적해요.

## 1. 진입 — 무엇이 있는지부터


| 읽는 값 | 쓰는 곳 |
|---|---|

| `result.slots.tokens` | 표 0 의 진실 원천. 비면 `references/color-type.md` §6~§12 기본 세트로 신설 |

## 2. 모드 결정 — 두 축, 각각 한 줄 근거

| 축 | 값 | 판정 기준 |
|---|---|---|
| 일 | **리뷰** | 이미 있는 화면(스크린샷 · 시안 · 코드 · 스토리북)을 검토 |
| | **설계** | 새 화면 · 기능을 만드는 중, 또는 리뷰 결과를 고쳐 반영 |
| 미학 | **절제** (기본) | 커머스 · 업무 앱 · 대시보드 · 설정 · 폼 · 목록 · 상세 · 결과 — 예외 없이 |
| | **파격 허용** | 랜딩 · 포트폴리오 · 브랜딩 · 매거진으로 판정된 화면만 → `references/bold-mode.md` |

사용자가 "멋지게" 라고 했다고 파격이 되지 않아요. 화면 종류가 정해요. 파격이어도 §6 게이트는
하나도 면제되지 않아요.

**구조만 바꾸는 작업**(부품을 디자인 시스템으로 올리기 · 리팩터)은 설계 모드지만 목표가 "화면 그대로" 예요 —
전후 픽셀 비교로 증명해요 (`references/measure.md` §5).

## 3. 보는 눈 — 열자마자 1~2초

1. **시각적 앵커가 있나** — 시선을 붙잡는 타이틀이나 메인 비주얼이 하나 있는지. 없으면 그레이를
   아무리 깔아도 빈 공간 과다가 안 잡혀요.
2. **여백이 충분한가** — 글자 · 부품이 해상도에 비해 커서 화면을 꽉 막거나 아래로 잘리지 않는지.
3. **핵심이 가려지나** — 글래스 · 짙은 그림자 · 고채도 배경이 상품 · 이미지 · 숫자를 방해하지 않는지.

**핵심 정보(primary content)는 화면마다, 시트 · 레이어 · 팝업마다 하나씩** 적어요. 홈에만 적고
바텀시트엔 안 적으면 시트 안에서 다시 위계가 없어져요.

그다음 스스로 묻는 여섯 질문:

| 질문 | 잡아내는 것 |
|---|---|
| 시각적 앵커가 되는 타이틀이 있나, 대비 · 강조가 있나? | 위계 부재 |
| 이 화면에서 제일 먼저 보여야 할 것 하나는 뭔가? | 우선순위 미정 |
| 다 강조했으면 강조된 게 하나라도 있나? | 강약 실패 |
| 왜 카드를 두세 번 중첩하고 그레이를 깔았지? | 여백 · 글자로 못 나눔 |
| 상품이 수천 개일 때 이 비율 · 연출을 유지할 수 있나? | 운영 불가 |
| 실제로 누르고 스크롤할 때 진심으로 편한가? | UX 오작동 |

"전반적으로 어색하다" 는 거의 늘 **같은 역할의 부품이 화면마다 다른 수치**(주 버튼 40 과 52,
카드 안쪽 16 · 20, 그룹 간격 16 · 24)예요. 시안 한 장이나 코드 한 파일로는 안 보이고, 재야 보여요.

## 4. 고치는 순서 — 항상 이 순서로

장식을 제거하기 전에 색이나 이펙트를 손대면 문제가 어디서 오는지 안 보여요.

0. **텍스트 먼저** (설계) — 박스 · 그래픽 전에 전달할 내용의 1~4순위와 글자 계층. 그래픽 없이
   텍스트만으로 뜻이 통해야 해요.
1. **장식 제거** — 중복 카드 프레임 · 그레이 배경 · 글래스 · 짙은 그림자를 지우고 흰 바탕으로.
2. **레이아웃 구조** — 지그재그 · 오버랩을 풀고 좌측 정렬 또는 풀배열. 정보가 복잡하면 1 : 0.5 : 0.5.
   반복되는 대표 모듈의 디폴트 규격을 먼저 확정하고, 좌측 시작선을 맞춰요 (`references/layout.md`).
3. **위계** — 화면(시트)마다 **가장 큰 글자 ÷ 본문 ≥ 1.75** (본문 16 이면 28 이상). 본문 15~16,
   캡션 · 단위 13~14, 핵심 숫자 32~40. "카드 헤드라인이 앵커라서 22 면 충분" 은 규칙 회피예요 —
   22 ÷ 15 = 1.47 은 위계가 없는 거예요. 큰 글자가 없으면 핵심 숫자나 상태 문장 하나를 28 이상으로.
4. **여백** — 간격 스케일 **4 · 8 · 12 · 16 · 20 · 24 · 32 · 40 · 48 · 64 · 80** 안에서만. 부품 안 4~16,
   화면 좌우 16~24, 섹션 사이 32~80. **안 여백 < 바깥 여백** 이라야 그룹핑이 생겨요. 처음엔 확
   벌려 놓고 줄여요.
5. **색** — 배경은 무채색으로 톤 다운, **포인트 컬러는 화면에 하나** (주 CTA 또는 선택 탭).
6. **마감** — 버튼 44~56 · 라운드 12 또는 원형, 1px 선 10~20%, 그림자 Y 4~8 / 블러 12~24 / 3~12%,
   행간 130~150%, 자간 −2~−3%, 좌표 · 크기 소수점 제거.
7. **예외 케이스** (설계) — 긴 문자열 · 큰 숫자 · 모듈 증가 · 320 · 상태(디폴트 · 눌림 · 선택 · 비활성 ·
   로딩). 레이어는 **스크롤 소유**(레이어 전체 / 내부 독립 / 메인)와 **닫는 법 셋**(인디케이터 · 헤더
   드래그 · 바깥 딤 탭 · X)을 문장으로. 라이브러리 이름만 적으면 닫는 법을 적은 게 아니에요.

수치 상세는 `references/numbers.md`, 판단 근거는 `references/principles.md`.

| 20 | 예외 케이스 · 확장성 | 긴 이름, 천만 단위 가격, 같은 모듈 무한 반복 | 최대 글자 수 · 말줄임, 분기 설계, 리듬 코너 1~2개 |

## 6. 게이트 — 숫자를 적어야 통과

숫자 없이 ✅ 를 치지 않아요. 측정값이 비면 그 행은 ❌ 예요. 설계 단계에선 design-spec 표 7 에
"명세 값" 을, 실행 뒤엔 screen-designer 리포트에 "화면에서 잰 값" 을 적어요.

- 화면 · 시트마다 핵심 정보 한 줄
- 가장 큰 글자 ÷ 본문 ≥ 1.75 (실제 나눗셈: 28 ÷ 16 = 1.75)
- 간격 값이 전부 스케일(4 · 8 · 12 · 16 · 20 · 24 · 32 · 40 · 48 · 64 · 80) 안 — 실측값 나열
- 주 버튼 · 인풋 높이 ≥ 44, **화면을 넘어 같은 값** — 화면별 실측값 나열
- 화면 좌우 마진 · 카드 안쪽 여백이 화면을 넘어 같은 값
- 포인트 컬러 1개, 상태색은 아이콘 · 기호와 함께
- 탭 가능한 부품마다 터치 영역 ≥ 44 — 부품 이름 나열
- 선택형 부품마다 선택 / 비선택 / 비활성 세 상태
- 레이어마다 스크롤 소유 + 닫는 법
- 버튼 라벨 행동 동사형, 상태어("완료" · "등록됨") 없음
- 금지어 0건 — 검색 결과 건수 (`references/ux-writing.md` §12)
- 실패할 수 있는 행동마다 오류 문구
- 완료 문구가 대상 · 수량 · 시각 중 둘 이상
- 숫자 + 단위는 크기 또는 굵기를 분리
- 같은 라벨 · 같은 행동 버튼이 한 화면에 하나
- 하단 고정 CTA 가 있으면 뒤 배경 페이드 + 스크롤 하단 여백
- 다크 테마면 배경 · 카드 · 보조 버튼 · 비활성 면이 눈으로 갈림
- 사용자 상태를 말하는 문구는 보여 주는 순간 참
- 긴 문자열 · 큰 숫자 · 320 처리

## 7. 절대 금지와 조건부 허용

**금지**: 커머스 목록에서 썸네일 비율을 화면마다 바꾸기 · 글래스 도배 · 브랜드 원색을 사방에 ·
그레이 · 카드 컨테이너 2중 3중 · 모든 요소 강조 · 딤으로 막아 놓고 스크롤 구역을 안 나누기 ·
지그재그 · 사용성 없는 컨셉보드를 실무 시안으로 내기.

**조건이 맞으면 허용** (판단 근거를 리포트에): 글래스는 하단 독바 · 바텀시트에서만 60~70% + 블러
20~30 · 대형 폰트 120~400 은 타이포 자체가 콘텐츠일 때 · 세로 썸네일은 매거진 · 미디어 · 카드
컨테이너는 박스 전체가 클릭 타겟일 때 · 이미지 위 딤은 10~30% 가독성용만. 전체 표는 `references/dos-donts.md`.

## 8. 문구 — 느낌이 아니라 논리로

화면에 글자가 생기면(버튼 · 에러 · 알림 · 제목 · 빈 상태) 이 순서예요. 10단계 상세와 전 · 후는
`references/ux-writing.md` §13, 다른 언어로 옮기는 법은 §12.

1. 말투가 아니라 정보 축부터 → 2. 상황 · 동기 · 기대 결과 → 3. 핵심 정보 하나 → 4. 정보 위계로
먼저 살아남고 그다음 보이스 → 5. 소리 내어 읽기 → 6. 익숙한 단어 의심 (버튼은 행동 동사형, 상태어
금지) → 7. 단위 먼저 확정 → 8. 같은 명사 반복 금지 → 9. 결론 줄 아래 겨루는 줄 금지 → 10. 약속은
보여 주는 순간 참.

한국어 화면이면 `references/locale-ko.md` (해요체 · 어절 줄바꿈 · 금지어 · 숫자 표기).
문구는 **한 파일에 모아요** (strings · copy · i18n) — 그래야 금지어를 전수 검색할 수 있어요.

## 9. spec-first — design-spec 표 0~7

설계 모드에선 화면을 그리기 전에 `references/spec-template.md` 의 표를 **그 열 그대로** 채워요.
산문 명세는 빈 칸이 안 보여서 상태 · 단위 · 오류 문구가 새요. 표는 빈 칸이 보여요.

| 표 | 무엇 | 빠지면 |
|---|---|---|
| 0 공통 토큰 | 글자 · 간격 · 포인트 · 무채색 · 상태색 · 라운드 · 선 · 그림자 · 아이콘 | 화면마다 다른 수치 |
| 1 화면 | 화면 · 시트마다 핵심 정보 + 가장 큰 글자 ÷ 본문 나눗셈 + 정보 순서 | 평평한 위계 |
| 2 부품 | 탭할 수 있는 모든 것 — 크기 · 터치 영역 · 상태 세 열 | 터치 미달 · 선택 상태 불명 |
| 3 숫자 표기 | 숫자와 단위의 크기 · 굵기 분리 | 숫자가 안 튐 |
| 4 문구 | 보이는 글자 전부 + 금지어 검색 건수 | 매번 문구를 다시 고침 |
| 5 레이어 | 스크롤 소유 + 닫는 법 | 갇힌 스크롤 |
| 6 예외 | 긴 문자열 · 큰 숫자 · 많은 항목 · 320 · 오프라인 · 0건 | 실제 데이터에서 터짐 |
| 7 자기 검수 | 게이트마다 명세 값 + ✅/❌ | — |

**빈 칸 규칙**: 값 또는 `해당 없음(이유)`. `—` · `TBD` · 공란은 미완성이에요. 파일이 있으면 **바뀐 행만**
고쳐요. 부품 선택이 헷갈리면 목적으로 골라요 (`references/principles.md` E4), 시스템마다 값이 다른
자리는 `references/component-systems.md`.

**멈추지 않아요.** 사용자가 정해야 할 것(버튼 통일 높이 · 선 vs 여백 · 앱 결 · 헤드라인 아래 무엇)은
후보 2~4개 + 권장 하나 + 이유를 적고 **권장값으로 진행**해요. 리포트 끝 "결정 필요" 에 모아요.
예외는 되돌리기 비싼 것 하나 — **기존 토큰 값을 바꿔 다른 화면이 깨질 때**는 바꾸기 전에 물어요.

```
⛔ 기존 토큰 button.height.md 를 40 → 52 로 바꾸면 호출부 14곳이 같이 바뀌어요
 🎯 정할 것: 주 버튼 높이 통일값
   ●  [a]  52 로 토큰 변경 + 14곳 스크린샷 재측정      ✅ 권장 — 화면 6개 중 4개가 이미 52
   ○  [b]  새 토큰 button.height.cta 52 를 추가, 기존 값 유지
   ○  [c]  40 유지 — 터치 44 미달은 hitSlop 으로
```

## 10. 실행 — screen-designer 를 새 컨텍스트로

리뷰만 하고 끝나는 경우(정적 스크린샷 한 장 · 코드도 실행 환경도 없음)는 이 skill 이 §12 형식으로
직접 리포트해요. **코드를 만들거나 고치거나, 돌아가는 화면을 재야 하면** `Agent` 도구로
`goax:screen-designer` 를 띄워요 (vendor 설치면 `screen-designer`). **이 대화를 넘기지 않아요.**
브리프에 넣는 건 이것뿐이에요:

- **요청 한 줄** — 사용자가 원한 것 그대로
- **모드 두 줄** — 일(리뷰 / 설계) · 미학(절제 / 파격 허용) + 각 근거 한 줄 (§2)
- **design-caps 결과** — `design-caps.sh --json` 의 `result` 를 그대로
- **references 경로** — `REFS="${CLAUDE_SKILL_DIR}/references"` 를 절대경로로 풀어서. 에이전트는 이 디렉터리의
  파일을 매 호출 직접 읽어요
- **design-spec 경로** — `result.spec` 또는 신설할 경로
- **대상** — 화면 · 파일 · 라우트 · 딥링크 (아는 만큼)
- **리포트 경로** — `docs/design/reports/<YYYY-MM-DD>-<screen-slug>.md` (사용자가 다른 곳을 원하면 그곳)
- **첫 줄 계약** — `verdict: 통과 | 보강 필요 | 실측 아님`

```bash
REFS="$(cd "${CLAUDE_SKILL_DIR}/references" && pwd)"   # 플러그인 references 의 절대경로 — 브리프에 그대로
REPORT="docs/design/reports/$(date +%F)-<screen-slug>.md"
```

여러 화면을 한 번에 맡길 땐 화면 하나(또는 한 흐름)에 에이전트 하나예요. 같은 토큰 파일 · 공용
부품을 여러 에이전트가 동시에 고치면 서로 덮어요 — 공용 파일을 건드리는 화면은 순서대로.

## 11. 판정 — 리포트 첫 줄

에이전트가 리포트 파일을 직접 써요. 이 skill 은 받아 적지 않고 **첫 줄만** 읽어 판정해요:

```bash
head -1 "$REPORT"
```

| verdict | 뜻 | 다음 |
|---|---|---|
| `통과` | 게이트 전 행에 **실측값**(스크린샷에서 잰 px)이 있고 전부 ✅ | 리포트의 전후 스크린샷 · 게이트 표 · 결정 필요를 사용자에게 보여 줘요 |
| `보강 필요` | 3회 고친 뒤에도 ❌ 가 남음 | "미해결" 을 그대로 보여 주고, 결정 필요 항목이 원인이면 사용자에게 고르게 해요. 다시 띄울 땐 미해결만 브리프에 |
| `실측 아님` | render 또는 measure 가 없어서 코드값 · 눈으로만 판정 | **통과로 바꿔 말하지 않아요.** 무엇이 없어서 못 쟀는지와 사용자가 직접 캡처할 방법을 보여 줘요 |

첫 줄이 셋 중 하나가 아니거나, 리포트 파일이 없거나, `통과` 인데 스크린샷 경로나 게이트 측정값 열이
비어 있으면 **판정 불가**예요 — 그 사실을 보고하고 에이전트를 다시 띄워요. 직접 고쳐 쓰지 않아요.

```
◆  screen — 판정

 ✅ verdict: 통과 — 게이트 19/19, 수정 2회차
 📂 docs/design/reports/2026-10-04-booking-confirm.md · docs/design/design-spec.md (표 1·2·4 행 추가)
 👉 결정 필요 1건 — 버튼 라운드 12 vs 원형 (진행은 12)
```

마무리에 HUD 를 갱신해요 (실패해도 본 작업엔 영향 없어요):

```bash
bash .ax/scripts/bash/update-state.sh --skill screen || true
```

## 12. 리뷰 리포트 형식 (정적 리뷰 · §10 에서 skill 이 직접 할 때)

지적은 **증상 → 원인 → 고침(수치)** 셋이 다 있어야 하나로 쳐요. 원인 없는 지적은 취향이고, 수치 없는
고침은 실행이 안 돼요. 첫 줄은 이 경우에도 verdict 예요 — 정적 이미지만 봤으면 `verdict: 실측 아님`.

```
verdict: 실측 아님
## 첫인상 (1~2초)
시각적 앵커: 있음/없음 — 무엇이 · 여백: … · 가려짐: …
핵심 정보: <무엇이 먼저 보여야 하나>
## 지적 (심각한 순, 패턴 번호)
1. [P1 위계] 증상: … / 원인: … / 고침: 타이틀 18→28, 본문 20→16
2. [W 관성어] 증상: "완료" 단독 / 원인: … / 고침: "9월 21일 04:30 2명 예약됐어요"
## 고치는 순서 — 이 화면에서 실제로 손댈 단계
## 잘한 것 (있으면)
## 프로젝트 규칙과의 충돌 (있으면)
## 구현 메모 (코드로 받았을 때만)
```

## 13. 낯선 화면 — 기능으로 붙여요

도메인 이름(농장 · 정비소 · 학원)으로 찾지 말고, 화면이 하는 일로 가장 가까운 유형을 골라 그 규격을
가져와요 (`references/screens.md`).

| 화면이 하는 일 | 가져올 유형 |
|---|---|
| 여러 항목을 훑는다 | 상품 목록 / 피드 · 타임라인 / 리스트 행 |
| 하나를 자세히 본다 | 상품 상세 / 예약 · 주문 확인 (핵심 → 부가 → 하단 고정 CTA) |
| 값을 넣는다 | 로그인 폼 / 글쓰기 · 에디터 / 금액 입력 (인풋 상태 · 키보드 위 액션) |
| 하나를 고른다 | 옵션 선택 바텀시트 / 캘린더 / 칩 · 세그먼트 |
| 잠깐 떠서 묻는다 | 바텀시트 · 모달 · 확인 대화상자 (스크롤 소유 + 닫는 법) |
| 숫자로 요약한다 | 대시보드 / 개인 통계 (숫자가 앵커, 차트는 보조) |
| 처음이거나 비었거나 막혔다 | 온보딩 / 빈 상태 / 에러 문구 절차 |
| 관리자가 표로 다룬다 | 대시보드 · 관리자 + 표 규칙 |

어느 줄에도 안 붙는 화면(지도 · 미디어 재생 · 채팅 · 게임)은 §4 순서 · §6 게이트 · 부품 규격만
적용하고, 그 화면 고유 규칙은 이 skill 밖이라고 리포트에 적어요.

## 16. 적용 범위

- **잘 맞는 화면**: 웹 · 커머스 · 업무 앱 · 대시보드 · 포트폴리오 · 랜딩, 모바일 앱 기본 화면.
  스택은 web · React Native · Expo · Lynx · Flutter · SwiftUI · Android 어디든 — 단위는 1배수 논리 단위.
- **원칙만 빌리는 화면**: 게임 · 미디어 플레이어 · 지도 · 채팅.
- **수치의 성격**: 실무 표준 범위이지 보편 법칙이 아니에요. 프로젝트 토큰이 이겨요.
- **범위 밖**: 사람 얼굴 · 외모를 평가하는 문구, 특정 사용자군을 낙인찍는 표현은 쓰지 않아요.

## 안티패턴

- **실행 에이전트의 리포트를 받아 적거나 고쳐 쓰기** — 검사받는 쪽이 검사 기록을 쓰게 돼요
- **`실측 아님` 을 통과처럼 말하기** — "대체로 괜찮아 보여요" 로 바꿔 전하지 않아요
- **스크린샷 없이 "확인했어요"** — 경로와 px 숫자가 증거예요
- **화면부터 그리고 표를 나중에 맞추기** — 표가 화면의 결함을 그대로 베껴요
- **매 단계 사용자에게 묻기** — 권장값으로 진행하고 끝에 모아요 (토큰 값 변경만 예외)
- **도구가 없다고 멈추기** — 대체 수단으로 끝까지 가고, 못 한 것만 정직하게 적어요
- **레퍼런스의 겉모습을 옮기기** — 옮기는 건 정보 순서와 이유뿐이에요
