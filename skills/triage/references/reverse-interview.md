# References — Reverse Interview 질문 축 (triage 4단계 상세)

> 구현 시작 전 AI가 사용자를 인터뷰해서 **놓친 요구사항을 발굴**하는 게이트예요.
> "뭘 시키느냐"가 아니라 "내가 뭘 모르는지"를 채우는 방향 — 질문의 목적은 분류(0단계)가 아니라 요구사항 발굴이에요.

## 프로젝트 오버라이드

프로젝트에 `.ax/docs/reference/reverse-interview.md` 가 존재하면 **그 파일이 이 기본 축을 대체**해요.
도메인 특화 축(예: 커머스의 동시성·멱등성, 프론트엔드의 접근성·브라우저 매트릭스)은 프로젝트 쪽 파일에 얹으세요.

## 기본 질문 축 (범용)

한 작업에서 **3~5개 축**만 골라요. 축마다 multiple choice 우선. `intent_notes` 에 이미 답이 있는 축은 건너뛰어요.

| 축 (key) | 캐는 것 | 질문 예 |
|---|---|---|
| `scale` 규모/부하 | 데이터·트래픽·호출 빈도의 자릿수 | "이 기능이 다루는 규모는? [a] 수십 건 [b] 수천 건 [c] 수백만 건 — 자릿수에 따라 설계가 달라져요" |
| `failure` 실패 모드 | 실패 시 복구 방법 — 롤백·재시도·멱등성 | "중간에 실패하면? [a] 그냥 재실행 OK (멱등) [b] 롤백 필요 [c] 부분 성공 허용 안 됨 (트랜잭션)" |
| `boundary` 경계 | 건드리면 안 되는 인접 모듈·계약 | "이번 작업에서 절대 건드리면 안 되는 영역이 있나요? [a] 없음 [b] 있음 (어디?) [c] 모르겠음 → blind-pass 로 정찰" |
| `done` 성공 기준 | 측정 가능한 "됐다"의 정의 | "완료를 뭘로 확인하죠? [a] 테스트 통과 [b] 특정 시나리오 동작 [c] 수치 개선 (지표?)" |
| `constraints` 제약 | 마감·호환성·금지 기술 등 외부 제약 | "지켜야 할 제약이 있나요? [a] 없음 [b] 하위 호환 필수 [c] 특정 버전/기술 고정" |

축 key 는 `.ax/current-task.json` 의 `intent_notes` 객체 key 와 1:1 — 0단계 인터뷰가 이미 `done` 이나 `constraints` 를 받았다면 4단계에서 재질문하지 않아요.

## blind-pass (낯선 영역 정찰)

처음 만지는 코드베이스/도메인이면 **질문보다 정찰이 먼저**예요. 역면접 첫 라운드를 blind-pass 로 시작:

1. AI 가 먼저 해당 영역을 스캔 — 자주 깨지는 지점, 엣지케이스, 기존 유사 구현, 숨은 의존
2. 정찰 결과를 요약해 보여주고, 거기서 나온 **구체적 불확실성**을 질문 축으로 변환
3. 정찰 없이 일반론 질문("실패하면 어떡하죠?")을 던지는 건 blind-pass 가 아니에요 — 정찰이 질문을 구체화해야 해요

기록: 정찰 요약은 `intent_notes.blind_pass` 에 한 줄로.

## 안티 패턴

- 축 5개를 기계적으로 전부 질문 — 작업과 무관한 축은 빼요. 축 선택 자체가 판단이에요
- 정찰 가능한 것을 질문 — 코드를 읽으면 알 수 있는 건 blind-pass 로 스스로 채워요. 질문은 코드에 없는 것(의도·제약·기준)만
- 자유 텍스트 강요 — 0단계와 같은 원칙. 옵션 본문에 예시·트레이드오프를 담아 사용자 인지 부하를 옵션 쪽에 부담
