# parallel — 레인 설계 + 게이트

## 시작 전 필수
`.ax/spirit/values.md`, `tone.md` 따라요.

## 발동 트리거
- `/parallel`
- "병렬로 돌리자", "레인 나눠줘", "갈래로 쪼개줄래", "에이전트 몇 개로"
- "이거 동시에 할 수 있어?", "핫 파일 뽑아줘"
- `spec-tasks` 를 막 끝냈고 `spec-implement` 로 들어가기 직전

## 0. 이 skill 의 범위

`spec-tasks` (분해) → **`parallel`** (가르기 + 게이트) → `spec-implement` (실행).

이 skill 은 **가르는 법**과 **정지 조건**만 담당해요. task 를 실제로 돌리는 건
`spec-implement` 이고, 여기서 에이전트를 띄우지 않아요. 레인을 설계하고 게이트를
통과시킨 결과물은 `tasks.md` 에 남아요 — 대화에만 있으면 다음 세션이 못 봐요.

> **"병렬로 가지 마세요" 도 이 skill 의 정당한 출력이에요.** 레인을 그리는 게 목적이
> 아니라, 가를 수 있는 일인지 판정하고 가를 수 있을 때만 깨끗하게 가르는 게 목적이에요.

---

## 1. 가를 수 있는 일인가 — 첫 관문

**병렬은 기본값이 아니라 정당화가 필요한 선택이에요.** 근거를 도구 만든 쪽이 직접
달아 뒀어요:

> "Most coding tasks involve fewer truly parallelizable tasks than research…
> LLM agents are not yet great at coordinating and delegating to other agents in
> real time." — Anthropic, *How we built our multi-agent research system* (2025-06-13)

같은 글이 멀티에이전트를 단일 챗 대비 **약 15배 토큰**으로 보고해요. 실측도 양극이에요
— 암묵적 조율에 맡긴 병렬은 **21% 가속 / 39% 감속** 사이에서 갈려요. 그래서 값을
치를 만한지부터 봐요.

> **"Subagents are a partitioning tool, not a speed button."**
> 가치는 몇 개를 띄우느냐가 아니라 **얼마나 깨끗하게 잘랐느냐**에서 나와요.

### 판정 체크리스트 — 하나라도 걸리면 단일 레인

| # | 질문 | 걸리면 |
|---|---|---|
| 1 | 지금 **어떤 파일을 건드릴지** 아나요? | 아직 모르면 판정 불가 — §2 로. 탐색부터 |
| 2 | 변경이 여러 레이어를 **동시에 관통**하나요? (메트릭·트레이싱·검증 규칙을 여러 레이어에 함께 심는 cross-cutting refactor) | **정의상 사전 분할이 안 돼요** — 단일 레인 |
| 3 | A 가 B 보다 먼저여야 하는 **순차 의존이 지배적**인가요? | 큰 컨텍스트의 **단일 에이전트**가 나아요 |
| 4 | 공유 인터페이스·이름·스키마를 **이번에 새로 정하는** 일인가요? | 결정이 먼저. 결정을 내린 뒤에 레인 |

2번이 특히 함정이에요. cross-cutting refactor 는 "파일이 많으니 나누면 빠르겠다" 처럼
보이는데, 나눌 경계가 파일이 아니라 **한 덩어리 결정**이라 자를수록 레인마다 다른
결론을 내요. 파일 수는 분할 가능성의 근거가 아니에요.

### 단일 레인으로 판정했을 때

레인 표를 그리지 말고 그렇게 답하고 끝내요.

```
🚦 parallel — 단일 레인 권장

 ▸ 사유  cross-cutting (검증 규칙을 4개 레이어에 동시 주입) — 사전 분할 불가
 ▸ 근거  경계가 파일이 아니라 한 덩어리 결정이에요. 나누면 레인마다 다른 규칙을 만들어요
 ▸ 대신  큰 컨텍스트 단일 실행으로 "/spec-implement"
```

## 2. 탐색이 먼저 — 계획 단계엔 병렬을 걸지 않아요

**탐색·계획 단계는 병렬 대상이 아니에요.** 굳이 나눠야 하면 **read-only 병렬만** 써요
(조사 레인, §4).

이유가 기계적이에요. §7 의 게이트는 `files:` 를 대조해서 성립하는데, 아직 어떤 파일을
건드릴지 모르는 단계에서 병렬을 걸면 **게이트가 빈 데이터를 검사해요.** "violations 0"
이 나오지만 그건 안전하다는 뜻이 아니라 검사할 게 없었다는 뜻이에요.

처방은 한 줄이에요:

> **"ask for the change plan, not the change"** — 무엇을 바꿀지가 아니라
> **어디를 건드릴지**를 먼저 받고, 그 다음에 자릅니다.

실측 순서 (오늘 세션): 조사 4갈래를 **read-only 로 먼저** 돌리고 → 나온 파일 목록으로
실행 레인 5개를 그었어요. 순서를 뒤집으면 소유권을 추측으로 나누게 돼요.

## 3. 두 축 판정 — 지금이 조사인가, 실행인가

레인을 가르는 축이 국면마다 달라요.

| 국면 | 가르는 축 | 왜 |
|---|---|---|
| **조사·검토** | 역할 / 도메인 | 읽기는 겹쳐도 아무 일도 안 생겨요. 같은 파일을 다섯 명이 봐도 손해가 없으니, 겹침이 아니라 **관점**으로 갈라야 산출이 안 겹쳐요 |
| **실행** | 파일 소유권 | 쓰기는 서로의 암묵적 결정을 못 봐요. 각자 멀쩡한데 합치면 양립 불가능해요 |

두 축은 **한 라운드 안에서 겹쳐요.** 조사가 끝나고 실행이 시작되는 게 아니라,
같은 라운드에 조사 레인과 실행 레인이 함께 도는 경우가 흔해요. 실측 라운드:

| 라운드 | 조사 갈래 | 실행 갈래 |
|---|---|---|
| 비주얼 방향 확정 | 역할 5레인 (레퍼런스 픽셀 분석 · 외부 디자인 언어 · 코드 인벤토리 · UX 갭 감사 · 스타일 후보) | 코드 미착수 |
| 비주얼 실행 | — | 파일 소유권 8레인 |
| 카피/UX | 역할 (Planner → Architect ∥ UX ∥ 레퍼런스 → Critic) | 파일 소유권 5레인, 겹치는 두 파일은 순서를 걸음 |
| 에이전트 전수조사 | 4갈래 | 파일 소유권 5레인 |

조사 레인은 `agents/lane-scout.md`, 실행 레인은 `agents/lane-worker.md` 를 써요.

## 4. 조사 레인 — 역할 / 도메인으로

- 레인마다 **다른 질문**을 줘요. 같은 질문을 다섯 번 물으면 다섯 개의 같은 답이 와요.
- 산출물 경로를 레인마다 다르게 지정해요. 한 파일에 다섯이 쓰면 그건 조사가 아니라 실행이에요.
- 조사 레인엔 편집 권한을 주지 마세요 — 조사 중에 고치기 시작하면 소유권 축이 무너져요.

## 5. 실행 레인 — 파일 소유권으로

> Phase 는 *논리적* 순서고, 병렬 실행의 단위는 **누가 어떤 파일을 쓰는가**예요.
> 같은 파일을 두 레인이 만지면 Phase 가 달라도 충돌해요.

이 한 줄이 이 skill 의 전부예요. Phase 2 와 Phase 4 에 흩어져 있어도 같은 파일을
쓰면 한 레인이어야 하고, 같은 Phase 안에 있어도 파일이 안 겹치면 다른 레인이어도 돼요.

## 6. 핫 파일 표 — 독점이냐, 떼어내기냐

핫 파일 = 여러 task 가 노리는 파일.

```bash
bash .ax/scripts/bash/lanes-hotfiles.sh --spec "$SPEC" --json
```

`result.hot[]` 이 파일별로 `tasks` (그 파일을 쓰는 미완료 task) 와
`parallel_claims` (그중 `[P]` 를 주장한 것) 을 줘요. `result.tasks_missing_files` 는
`files:` 를 안 적은 task 예요 — **여기부터 고쳐요.** 파일 경로가 없으면 겹침 검사가
그 task 엔 아예 닿지 않아서, 게이트가 "위반 없음"이라고 말하는데 실제로는 검사가
안 된 상태가 돼요.

### 정책 둘 — 독점만이 답이 아니에요

| 정책 | 무엇 | 언제 |
|---|---|---|
| **A. 독점** | 그 파일을 만지는 task 를 **한 레인**에 몰아줘요 | 레인마다 그 파일에서 **서로 다른 판단**을 하려 할 때. 합쳐 놓아야 결정이 하나로 서요 |
| **B. 떼어내기 (순차 큐)** | 공유 부분만 **별도 task** 로 떼어 순차로 돌리고, 나머지는 병렬로 남겨요 | 레인들이 그 파일에서 원하는 게 **같은 종류의 기계적 변경**일 때 — 배럴 내보내기, 인덱스, 등록부, 라우팅 테이블, i18n 카탈로그 |

**판단 기준 한 줄**: 각 레인이 그 파일에 넣으려는 게 *같은 모양의 한 줄*이면 B,
*서로 다른 결정*이면 A 예요.

B 가 오늘 세션이 실제로 쓴 방법이에요. 표면 컴포넌트 5개가 전부 배럴
`packages/ui/src/index.ts` 를 공유했는데, 다섯이 원한 건 각자 `export` 한 줄씩이라
**배럴 내보내기만 `T009` 로 떼고 나머지 5개를 병렬로 뒀어요.** A 로 갔으면 표면 5개가
한 레인에 묶여 병렬이 사라졌을 거예요.

세 번째 길도 있어요 — **순서를 건다** (`의존:` 명시). 떼어낼 경계는 없는데 두 task 가
시점만 다르면 이게 제일 싸요.

뽑은 결과를 `tasks.md` 에 표로 박아요. 대화에 흘리면 다음 세션이 못 봐요.

```markdown
## 1.5 핫 파일 — 소유 레인 고정

| 파일 | 노리는 task | 정책 | 처리 |
|---|---|---|---|
| `packages/ui/src/index.ts` | T010~T014 | B 떼어내기 | 배럴 내보내기를 T009 로 분리, T010~T014 에서 제거 |
| `apps/mobile/src/screens/Result.tsx` | T021, T034 | A 독점 | 레인 A 가 둘 다 — 레이아웃 판단이 하나여야 해요 |
| `packages/core/src/rules.ts` | T041, T052 | 순서 | T052 는 T041 뒤로 (`의존: T041`) |
```

소유자 배정은 **판단**이에요 — 스크립트는 경합 사실만 주고 누가 가질지는 정하지 않아요.

## 7. 게이트 — `violations` 가 비어야 통과

```bash
bash .ax/scripts/bash/tasks-plan.sh --spec "$SPEC" --json
```

`result.violations` 가 비어 있지 않으면 **정지해요.** 레인을 띄우지 말고 tasks.md 를
먼저 고쳐요. 해소법은 §6 의 셋 — 독점 / 떼어내기 / 순서 — 이고, `[P]` 를 떼는 것도
언제나 유효한 답이에요 (순차는 느릴 뿐, 잘못된 병렬은 되돌리는 비용이 더 커요).

오늘 실측: 표면 컴포넌트 5개가 전부 배럴을 건드리면서 `[P]` 로 표시돼 있었고,
`tasks-plan.sh` 가 10쌍 violation 으로 잡았어요. 떼어내기(B)로 해소했어요.
**사람이 눈으로 못 본 것을 스크립트가 잡았어요** — 그래서 이 게이트는 형식이 아니라
실효가 있어요.

⚠ 이 게이트는 **§2 의 탐색이 끝난 뒤에만** 의미가 있어요. `files:` 가 비어 있으면
빈 데이터를 검사하고 통과시켜요.

## 8. 실행 순서 — 레인 간 의존

레인이 서로 안 겹쳐도 순서가 중요한 경우가 있어요. **논리를 바꾸는 일이 표현을
바꾸는 일보다 먼저** 와요.

오늘 사례: 버그 수정(논리 변경)을 카드 치환(스타일 변경)보다 먼저 걸었어요.
반대 순서면 치환된 코드 위에서 논리 변경을 다시 읽어야 해요.

## 9. 정지 조건 — 레인을 띄우기 전에 적어요

각 레인에 "이 조건이면 멈추고 보고" 를 미리 줘요. 없으면 전제가 틀렸을 때도 레인이
끝까지 밀어붙여요.

실전 예: "T050 이후 특정 오버라이드가 3곳 넘게 남으면 → 전제가 틀린 거예요.
계속하지 말고 남은 목록과 함께 보고하세요."

정지 조건은 **수를 세는 형태**가 좋아요. "이상하면 멈춰라"는 정지 조건이 아니에요.

## 10. 위임 브리프 — 이 다섯 줄은 빼지 마세요

레인마다 브리프를 쓸 때 아래를 그대로 넣어요. 하나하나가 실제 사고에서 나왔어요.

```markdown
## 소유 파일 — 이 목록 밖은 절대 건드리지 마세요
<파일 경로 나열>

## 금지 파일
<다른 레인 소유 · 공용 설정 · 버전 파일>

## 규율
- **커밋하지 않아요.** 워킹 트리에 변경만 남기세요. `git add -A` 는 특히 금지 —
  동시 세션의 파일까지 쓸어담아요.
- **정량 주장엔 근거 명령을 붙이세요.** "소비처 6곳" 처럼 세어서 말할 거면 센
  명령(`grep -rn ... | wc -l`)과 그 출력을 보고에 같이 넣으세요. 삭제 전엔 반드시
  `grep` 하고 결과를 보고에 포함하세요.
- **공유 이름을 바꾸면 즉시 보고하세요.** props 이름·타입 축·토큰 이름을 바꾸는 건
  파일 안의 일이 아니라 레인 밖의 일이에요.
- **결과를 반드시 `SendMessage` 로 전송하세요.** 파일을 다 만들고 idle 이 되는 건
  완료가 아니에요.
- 보고가 길면 **나눠서 여러 번 보내세요.** 한 번에 밀면 잘려요.
```

### 왜 이 규율인가 — 실제로 터진 사고 다섯

1. **두 세션이 한 산출물** — 파운더가 렌더 비교로 채택한 안을 다른 세션이 모른 채
   덮었어요. 커밋 메시지·ADR 은 새 안을 말하는데 바이트는 옛 안이었어요.
   근본 원인: *"산출물을 기준으로 소유자를 세지 않았어요. 파일이 아니라 작업 단위로만
   범위를 갈랐어요."*
2. **`git add -A` 가 다른 세션 파일 3개를 쓸어담음** — *"동시 세션 환경에서 '워킹
   트리는 내 것'이라는 단독 점유 가정."*
3. **위임 산출물이 아예 도착 안 함** — 세 에이전트가 241·96·167줄을 완성해 놓고
   `SendMessage` 없이 idle. 근본 원인: *"완료 판정을 '에이전트가 idle 인가'로 했고
   '산출물을 받았는가'로 하지 않았다."*
4. **레인 idle 을 완료로 오독** — 레인 8개가 전부 idle 이 되자 완료로 인식했는데 그
   시점 체크박스는 24/36 이었어요. *"Phase 와 레인을 1:1 로 착각했다."*
5. **번호 충돌** — 동시 세션이 ADR 번호를 겹치게 만들었어요.
   `next-spec-num.sh --reserve --slug <slug>` 의 `O_EXCL` 선점이 이걸 막아요. 레인이 문서를 새로
   만든다면 번호는 반드시 이 스크립트로 받으세요.

### 정량 주장은 문서에 적히는 순간 위험해요

계획에 이런 오차가 남았어요 — "소비처 6곳"이 실제 10곳, "사용처 0"이 실제로는 렌더
중, "import 함"이 실제로는 안 함. 셋 다 **브리프에 "삭제 전 grep 하고 결과를 보고에
포함하라"를 넣은 덕에** 실행 단계에서 걸렸어요.

> 정량 주장은 1인칭으로 말하는 시점이 아니라 **문서에 적히는 시점**에 이미 위험해요.
> spec 에 들어간 "N곳"·"사용처 0" 은 그 뒤 모든 실행자가 전제로 삼아요. 원 출처가
> 서브에이전트면 **근거 명령을 함께 적어** 재확인 가능하게 해요.

## 11. 산출물 수신 확인 — idle 은 완료가 아니에요

레인이 조용해지면 **받은 것**을 세요. 안 왔으면 재요청하되, 이렇게 적어요:

> 다시 하지 말고 **이미 만든 결과를 그대로 전송**하세요.

이 문장이 없으면 레인이 전체 작업을 처음부터 반복해요.

보고가 잘렸으면 (문장이 중간에 끊겼거나 섹션이 비었으면) **잘린 지점을 지목해서**
이어 보내달라고 해요 — "T3 섹션 3번째 항목부터 다시 보내주세요". "다시 보내주세요"
만 하면 앞부분이 또 오고 또 잘려요. 오늘 세션에서 서브에이전트 보고가 6번 잘렸어요.

## 12. 완료 판정 — 체크박스 **그리고** 통합 검증

### 12.1 체크박스

```bash
bash .ax/scripts/bash/tasks-gate.sh --spec "$SPEC" --json
```

`result.complete` 가 `true` 일 때만 완료예요. 아래는 **전부 완료가 아니에요**:

- 레인이 전부 idle 이다 → 사고 4. 레인 8개가 idle 인데 체크박스는 24/36 이었어요
- 에이전트가 "완료했습니다" 라고 보고했다 → 사고 3. 보고와 산출물 도착은 별개예요
- Phase 가 끝났다 → Phase 와 레인은 1:1 이 아니에요

게이트는 미완료 체크박스뿐 아니라 대응 task 없는 AC(`ac_uncovered`)와 task 유실
(`task_count_drop`) 도 봐요. 미완료를 지워서 통과시키는 길이 막혀 있어요.

### 12.2 통합 검증 — 파일이 안 겹쳤다고 합쳐서 도는 건 아니에요

**파일 소유권은 물리적 충돌만 막아요.**

> "git worktrees prevent parallel sessions from overwriting one another's files on
> disk, **but they do not prevent logical conflicts.**"

지배적 실패 모드는 덮어쓰기가 아니라 **레인들이 암묵적으로 상충하는 결정을 내리는 것**
이에요 — 공유 스펙이 없어서요. 파일 경계와 무관하게 나는 것들:

- 공유 전역 설정 · 환경변수 · feature flag
- DB 스키마 · 마이그레이션 순서
- 싱글턴 · 전역 레지스트리
- 공유 인터페이스 · props 계약
- **같은 개념에 서로 다른 이름을 붙이는 것** ← 제일 조용해요

오늘 실측: 한 레인이 `Pill` 의 축을 `tone` → `variant` 로 바꿨어요. 다른 레인이 그걸
모른 채 치환했으면 조용히 깨졌을 거예요 (레인 간 인수인계로 막았어요). 두 레인 다
자기 파일만 만졌는데도요.

**그래서 레인이 전부 끝난 뒤 전체 검증을 한 번 더 돌려요.** 레인별 검증은 레인별
사실만 증명해요.

```bash
pnpm typecheck && pnpm test        # 프로젝트의 전체 검증 (.ax/config.yml commands 참조)
```

그리고 명령으로 안 잡히는 것 하나 — **이름 대조**. 레인들이 새로 만들거나 바꾼
공유 이름(props·타입·토큰·이벤트)을 모아서 같은 개념에 두 이름이 생기지 않았는지
봐요. 레인 보고의 "다른 레인에 넘길 것" 항목이 그 목록이에요.

통합 검증까지 통과해야 완료예요.

## 13. 알려진 제약 — 이걸 모르면 게이트가 조용히 헛돌아요

- **`tasks-plan.sh` 는 의존 키워드를 한글 `의존:` 로 하드코딩해요** (`tasks-plan.sh:83`).
  `deps:`·`depends:` 는 안 읽혀요. "의존 없음"으로 인정되는 값은 `없음`·`none`·`-`
  뿐이에요. 다른 표기는 그 이름의 task 에 의존하는 걸로 읽혀서 영원히 blocked 가 돼요.
- **파일 겹침 검출은 task 줄에 파일 경로가 실제로 적혀 있어야 성립해요.** `files:` 가
  없으면 겹쳐도 violation 이 안 나와요. `lanes-hotfiles.sh` 의
  `tasks_missing_files` 가 이 사각지대를 보여줘요.
- `tasks-plan.sh` 의 `violations` 는 **ready 인 `[P]` 끼리만** 봐요. 지금 blocked 인
  task 가 나중에 만들 충돌은 안 잡혀요. 핫 파일 표가 그 자리를 메워요.
- **어떤 게이트도 의미적 충돌은 못 봐요.** 셋 다 파일 이름만 비교해요. §12.2 가
  사람 몫으로 남는 이유예요.

## 절대 금지

- **분할 가능성 판정을 건너뛰고 레인부터 그리기** — §1 이 첫 관문이에요
- **탐색 전에 병렬 걸기** — 게이트가 빈 데이터를 검사하고 통과시켜요
- **cross-cutting refactor 를 파일 수로 쪼개기** — 경계가 파일이 아니라 한 덩어리 결정이에요
- **violations 가 남은 채로 레인 띄우기** — 게이트는 통과 의례가 아니에요
- **레인 idle 을 완료로 읽기** — 완료는 `tasks-gate.sh` 의 `complete` + 통합 검증
- **통합 검증 없이 완료 선언** — 파일이 안 겹친 건 물리적 충돌이 없었다는 뜻뿐이에요
- **핫 파일 표를 대화에만 남기기** — 다음 세션이 못 봐요. `tasks.md` 에 박아요
- **레인에 커밋 권한 주기** — 합치는 건 한 사람이. `git add -A` 는 특히 금지
- **`files:` 없이 task 를 두고 병렬 판정하기** — 검사가 안 닿는데 통과로 보여요
- **조사 레인에 편집 권한 주기** — 소유권 축이 무너져요
- **레인 수를 먼저 정하기** — 레인 수는 핫 파일을 뺀 뒤 *남는 파일 묶음* 이 정해요
