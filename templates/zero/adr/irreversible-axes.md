# 되돌리기 비싼 결정 — 첫날 체크리스트

> 판정 기준은 **"기술이냐 제품이냐 비즈니스냐" 가 아니에요.**
> **"되돌리려면 무엇을 동시에 고쳐야 하나"** 하나예요. 답이 "파일 몇 개" 면 미뤄도 되고,
> **"전부"** 면 지금 역면접하고 ADR 로 남겨요.
>
> 실증 프로젝트는 **제품명을 3번, 비주얼 방향을 3번** 갈아엎었고 전부 ADR 대체로 처리했어요.
> 코드가 아닌 결정이 코드 결정보다 비쌌어요. 그리고 그 프로젝트 최대 실패가
> **혼자 정한 것**이었어요 — 파운더 원문 *"왜 내 인터뷰도 없이 너맘대로 만들엇어?"*,
> *"UX 라이팅도 너맘대로 하고"*. 비용은 아이콘 재작업 4회 이상.
> 5 Whys 근본 원인: **"되돌리기 어려운 결정과 그렇지 않은 결정을 구분하지 않았다."**
>
> 그래서 이 문서가 `zero` 스킬의 골격이에요.

## 판정 절차

1. 아래 축을 훑고 **이 제품에서 되돌리기 비싼 것만** 고릅니다 (보통 3~6개)
2. 고른 축마다 **역면접으로** 대안 2~3개를 꺼내고 기각 사유까지 받아요.
   긴 계획 문서를 던지지 말고 `AskUserQuestion` 으로 선택지를 물어요 — 실측으로
   계획 문서는 승인 대기로 멈췄고, 선택지로 물은 라운드는 사이클이 4.8h → 1.1h 로 줄었어요
3. **대신 정하지 않아요.** 정보가 부족하면 정보를 모아 선택지로 만들어 다시 물어요
4. 안 고른 축은 이 파일 맨 아래 "미결정" 에 이유와 재검토 시점을 적어요.
   **비어 있는 것과 의도적으로 미룬 것은 달라요**

ADR 본문 양식은 `.ax/_templates/adr/0000-template.md`. 번호는 손으로 고르지 말고 선점해요:

```bash
bash .ax/scripts/bash/next-spec-num.sh --kind adr --reserve --slug <slug> --json
```

## 기록 형식 (축 하나 = ADR 하나)

한 ADR 에 여러 축을 묶지 않아요. 묶으면 하나를 뒤집을 때 나머지가 인질이 돼요.

각 ADR 에 **반드시** 들어갈 것:

- 기각한 대안과 **기각 사유** (재제안 차단 — 이게 ADR 의 본체예요)
- 되돌리려면 무엇을 동시에 고쳐야 하는지 한 줄
- 이 결정이 **사람의 것인지** 표시 — 파운더가 고른 선택지는 그대로 인용해요
- 자동 집행이 가능하면 그 장치 경로 (`enforced_by: hook:...` / `external:...`)
