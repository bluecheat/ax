# 계약 카탈로그 — 규율 16개를 어디로 보냈나

> 실증 프로젝트 2주치에서 뽑은 정확도 장치 16개(선제 3 + 첫날 가능했던 13)를,
> **산문으로 남기지 않고 세 갈래로 갈랐어요.**
>
> - **(가) 계약·기계** 8개 — hook·스크립트·테스트·CI 로. 프롬프트 토큰 **0** 이에요
>   (hook 정의는 `settings.json` 에 살고 모델 컨텍스트에 안 들어가요)
> - **(나) 최소 산문** 7개 → **4개로 합침** — 기계가 판정 못 하는데 없으면 틀리는 것
> - **(다) 삭제** 1개 — 지금 모델·하네스가 이미 하는 일
> - **(신규)** 1개 — 파운더 사고에서 나온 `SP-REV-001` (되돌리기 비용 판정)
>
> 최종 산문은 `.ax/spirit/rules/zero-baseline.md` **5개**뿐이에요.

## 왜 이렇게 가르나

Claude Code 공식 best-practices 가 기준을 줍니다 — *"각 줄에 대해 물어라: 이걸 지우면 Claude 가
실수하게 되는가? 아니면 잘라라. 비대한 CLAUDE.md 는 Claude 가 실제 지시를 무시하게 만든다."*
그리고 *"CLAUDE.md 지시는 advisory 지만 hook 은 deterministic 하고 실행을 보장한다."*

정량 근거도 같은 방향이에요 — Chroma *Context Rot*(2025-07, 프런티어 18모델)은 입력이 길수록
성능이 비균일하게 떨어지고 distractor 하나만 있어도 저하된다고 통제 실험으로 보였어요.
IFScale(arXiv 2507.11538, 20모델)은 지시 500개 밀도에서 최고 모델도 **68%** 준수.
ManyIFEval 은 "all-or-none" 판정이 개별 평균보다 훨씬 낮다고 보고해요 — **규율 16개를 깔고
"다 지켜졌나" 로 판정하는 게이트가 정확히 그 구조**예요.

**반대로 하네스 자체는 지지받아요.** Harness-Bench(arXiv 2605.27922, 태스크 106 · 트라젝토리
5,194)는 같은 모델에서 하네스만 바꿔 **76.2% vs 52.4%, 23.8점 격차**를 보고하고, 실패 분류 1위가
**contract/format violation 36.4%** 예요. MAST(NeurIPS 2025)도 멀티에이전트 실패의 41.8%가 명세
문제, 21.3%가 검증 부재라고 해요. 결정론을 코드로 미는 쪽의 이득도 측정돼 있어요 — Anthropic
*Code execution with MCP*(2025-11-04)는 **150,000 → 2,000 토큰(98.7% 절감)** 을 보고합니다.

**두 진영은 다른 것을 말해요.** 지우라는 건 *모델에 주입하는 산문*이고, 점수를 만드는 건
*계약·도구·검증 루프*예요. 그래서 산문을 줄이고 계약을 늘립니다.

> 한 줄에 묶고 있어서, 장치가 달라 두 줄로 폈어요. 규율 수는 16개 그대로예요.

## 새 프로젝트에서 판정하는 법

새 룰을 쓰고 싶을 때마다 이 순서로 물어요.

1. **기계가 판정할 수 있나?** — 위반을 grep·테스트·exit code 로 잡을 수 있나
   - 예 → **(가)**. hook·스크립트·테스트로 만들고 **산문은 쓰지 않아요**
   - 애매 → 오탐률을 재 봐요. 오탐이 잦으면 사람들이 게이트를 끕니다. 끄느니 (나) 로
2. **모델이 지시 없이도 이미 하나?** — 최근 세션 5개에서 실제로 틀린 적이 있나
   - 없다 → **(다)**. 적지 않아요. 순손실이에요
3. 둘 다 아니면 → **(나)**. 단, **"이게 없으면 무엇을 틀리는가"** 에 한 줄로 답을 쓰세요.
   못 쓰면 그건 룰이 아니라 취향이에요

## hook 은 조용해야 해요

hook 은 공짜가 아니에요 — **출력이 컨텍스트에 들어가요.** 통과할 때 말하는 hook 은
(가)로 옮겨서 아낀 토큰을 도로 씁니다.

- 통과 = **아무 말도 안 함** (exit 0, 출력 0줄)
- 실패 = 한 줄. 무엇이 왜 막혔는지 + 고치는 법
- 진단·요약·"검사 완료" 류 출력 금지

## 상시로 재요 — 프로브는 첫날 1회가 아니에요

게이트가 살아 있는지는 계속 재야 해요. policy-as-code 실무의 정설이 그 이유예요 —
*"통제를 집행하는 것처럼 보이는 룰이 조용히 'false' 가 아니라 'undefined' 로 평가될 수 있고,
undefined 는 denied 와 다르다."*

`zero-probe.sh` 를 CI 에 넣어 매 푸시마다 돌리세요 (`ci-github-actions.yml` 에 이미 있어요).
실증 사례 — CI 가 의존성 설치 실패로 **한 번도 안 돌면서 초록**이었어요.
